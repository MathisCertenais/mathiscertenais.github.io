# 0001 — Machine-readable metadata for every canonical route

- **Status:** Accepted
- **Date:** 2026-11-23
- **Deciders:** Mathis Certenais
- **Related:** `src/content/siteRecords.ts`, `src/content/siteMetadata.ts`,
  `scripts/prerender-routes.mjs`, `scripts/check-routes.mjs`

## Context

The site is a bilingual React application served as static files. Every canonical route already
has a prerendered HTML shell with a title, description, canonical link and Open Graph tags. That is
enough for a search engine, but not for an answer engine or a research index: neither can tell,
without parsing prose, what a page is about, who wrote it, which works it cites, or where the same
page exists in the other language.

The editorial facts that answer those questions already exist in `src/content/siteRecords.ts`:
eight page records and ten article records, with summaries, keywords, named entities, citations,
authors and revision dates. The manifest already knows every canonical route, its French twin and
its legacy aliases. What was missing was a stable serialisation of those facts, attached to each
route and validated against the source.

Two constraints shaped the decision. First, `dist/` is committed and the build is deterministic:
the same source must produce byte-identical artifacts. Second, the client router replaces the
document on navigation, so the structured data in the head must be replaceable without a reload.
Third, the browser bundle must not import a Node module; only the build and the validator may hash
an article body.

## Decision

Every canonical route — page or article, English or French — carries two artifacts.

1. **JSON-LD.** One `<script id="page-jsonld" type="application/ld+json">` in the prerendered
   `<head>`, containing a `@graph` that always starts with the `Person`
   (`https://mathiscertenais.com/#person`) and the `WebSite`
   (`https://mathiscertenais.com/#website`), followed by the route node. The home graph is
   `[Person, WebSite]`; an article graph ends with the article node; every other page graph ends
   with its `WebPage`, `ProfilePage`, `CollectionPage` or `ContactPage`. `/insights` and `/videos`
   add a `hasPart` list. The JSON is pretty-printed with two spaces and every `<` is escaped to
   `\u003c`, so the block can never terminate its own script element.

2. **A `site-metadata@1` JSON file** at `jsonPathFor(path)`: `/` becomes `/index.json`, every other
   route appends `.json` (`/insights/sc26-europe` becomes `/insights/sc26-europe.json`). The file
   carries the route's identity, language, canonical URL, translations, manifest title and
   description, editorial summary, authors, dates, keywords, entities, resolved citations,
   licence, image and, for articles, the source block body (`article-blocks@1`), reading time and
   a `sha256:` content hash.

3. **`dist/llms.txt`** lists every canonical page and article in both languages, with its absolute
   URL, manifest description and JSON URL. It contains no legacy alias.

Legacy aliases and `/404` carry neither artifact: they are `noindex` redirects, and a second
description of the same content would compete with the canonical one. The client applies the same
JSON-LD on navigation through `applyStructuredData(pathname)`: it removes any existing
`script#page-jsonld` and inserts the graph for the canonical route, or removes it when the route is
an alias or the not-found page.

The builder is pure (`src/content/siteMetadata.ts`): no filesystem, no clock, no locale API, no
`import.meta`. `site.origin` is the absolute origin of the artifacts, not `VITE_SITE_URL`, so the
JSON-LD and the JSON files are identical whether or not a deploy origin is configured. The article
body hash is injected by the build and the validator with `node:crypto`; the client calls the same
builder without a hash and never imports a Node module.

The source validator (`pnpm check:routes`) checks the records themselves: every canonical route and
every `ArticleId` has a record, `schemaTypeFor` resolves, summaries are 80–700 characters and two or
three sentences, dates and licences have the agreed shape, keywords and entities are unique,
citations are unique and traceable to the article body or its `sourceHref`, `site.origin` matches
`public/CNAME`, every record round-trips through JSON, and every French canonical has an English
twin. The dist validator (`pnpm check:dist`) checks the output: one JSON-LD block per canonical
shell, none on aliases or 404, absolute `@id`s, the expected `@type`, `url` and `inLanguage`, one
JSON file per canonical route with a recomputed content hash, a byte comparison against the
builder, `llms.txt` with every canonical URL exactly once, and no orphan `dist/**/*.json`.

## Consequences

- `dist/` gains thirty-six JSON files and `llms.txt`. They are generated by `pnpm build` and
  committed with the rest of the output; they must never be edited by hand.
- `src/content/siteRecords.ts` is now an editorial dependency of the build and the client. A fact
  added there reaches the JSON-LD, the JSON files and `llms.txt` in one change.
- The French twins use the English display date as the source of truth. French dates are
  translations (`13 septembre 2026`), and parsing them would create a second date grammar with no
  benefit: the publication day is the same fact in both languages.
- The two home titles carry no ` | Mathis Certenais` suffix. `stripSiteSuffix` returns them
  unchanged and throws only when a title carries a different site suffix, rather than rejecting a
  valid title.
- A page record with `dateModified: null` omits the property from JSON-LD and writes `null` in the
  JSON file. No build timestamp or last-commit date is substituted.
- The client rebuilds the JSON-LD on navigation from the same records, so a record change is
  visible without a reload. The content hash is absent from that client-side object and present in
  every built artifact.

## Open questions

- **Site licence.** `site.license` is `null`: no `license` property in JSON-LD, `license: null` in
  the JSON files. Choosing a licence is a legal decision, not a metadata default.
- **ECLAT interview day.** The article prints “September 2025” and the repository records no day.
  `datePublished` is therefore `2025-09`, and `dateModified` uses `2025-09-01` as a month anchor.
  The exact day should replace both once it is known.
- **Page `dateModified`.** Every page record is `null`. The site has no page-level revision history
  that can be told apart from a content-wide commit; a date should be added only when a page is
  revised on its own.
- **Peer-review status of the SC26 paper.** `exascale-astronomy-cybersecurity` is typed `Article`.
  If the SC26 workshop paper is peer-reviewed, `ScholarlyArticle` is the accurate schema type and
  the record should change.
- **ORCID and affiliation URLs.** `site.person.sameAs` contains the LinkedIn profile only, and
  `affiliation` carries names because the repository has no verified page for IRISA or Université
  de Rennes. An ORCID identifier and institutional URLs should be added when they can be checked.
- **WCAG 2.1 versus 2.2.** `AGENTS.md` requires WCAG 2.2 AA, while the accessibility page and
  `docs/rgaa-audit.md` say WCAG 2.1. The wording must be aligned before the site claims
  conformance to either version.
